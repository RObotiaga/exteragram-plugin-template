# Template Architecture

This reference describes the intended architecture of `RObotiaga/exteragram-plugin-template`
and forks created from it. Always compare it with the current branch before applying a rule.

## Purpose of the template

The template combines two execution layers in one installable Elyx/EAF plugin:

- Python runs inside exteraGram through Chaquopy and owns the `BasePlugin` lifecycle,
  settings/menu integration, orchestration and the Python side of the bridge.
- Kotlin is compiled to Android bytecode and then to `classes.dex`. It is loaded at runtime
  and is suited to complex JVM integration, reusable Java-facing logic and hot/high-frequency
  hooks where a JVM implementation is clearer or cheaper.

The release artifact is one `.eaf`, but the source project is intentionally multi-file.

## Canonical repository areas

The exact names can evolve, but the current architecture is centered around:

```text
repo/
├── refmap.yml
├── metainfo.yml
├── <plugin-entry>.py
├── plugin_src/
│   └── ... Python modules ...
├── assets/
│   └── ... static project resources ...
├── src/main/kotlin/
│   └── ... Kotlin/JVM implementation ...
├── libs/
│   ├── Telegram.jar
│   └── Telegram-compile.jar
├── tools/
│   ├── build_eaf.py
│   ├── embed_dex.py
│   └── dev_watch.py
├── scripts/
│   └── prepare_release.py
├── build.gradle.kts
├── justfile
└── .github/workflows/
```

Do not infer generated paths only from this document. Read the actual Gradle tasks and
`tools/build_eaf.py` when changing the pipeline.

## Canonical EAF layout

The template's structured artifact is conceptually:

```text
<plugin-id>.eaf
├── refmap.yml
├── metainfo.yml
├── main.py
├── assets/
│   ├── classes.dex
│   └── ... project assets ...
└── src/
    └── ... additional Python modules ...
```

`main.py` is a release copy/name of the repository's Python entry module. It must remain
normal Python source in the EAF build; do not inject DEX hex into it.

`assets/classes.dex` is generated by the build and is reserved. A source asset with the
same archive path must not silently replace the generated DEX.

Declared Elyx directories are part of the archive contract. A child entry such as
`assets/classes.dex` does not necessarily create a real `assets/` ZIP directory entry for
strict installers, so the builder should emit/validate explicit declared directory entries.

## Python ↔ JVM bridge

Keep the bridge small and explicit.

A robust bridge normally owns:

- resolving/loading the DEX bytes;
- creating an `InMemoryDexClassLoader` or another deliberately chosen class loader;
- loading one stable JVM entry class;
- invoking a small number of explicit static/instance methods with exact Java types;
- converting/logging errors without letting them disappear across the Python/JVM boundary;
- invalidating references on unload/eject.

Avoid making Python reflectively call dozens of arbitrary Kotlin methods scattered through
the project. Prefer one JVM facade/entry class and ordinary Kotlin calls behind it.

When adding a bridge method, document:

```text
Python name/call site
JVM declaring class
JVM method name
static/instance
parameter Java types in order
return type
failure behavior
lifecycle ownership
```

This turns bridge changes into a reviewable contract instead of stringly-typed reflection.

## DEX resource loading

For structured Elyx, binary DEX belongs in assets. The public Elyx API can expose binary
assets using `from elyx import assets` and `content_bytes()`, and each `Asset` also exposes a
resolved filesystem path.

Do **not** assume Elyx defines Python `__file__`. Real AyuGram/Elyx device validation showed
that `main.py` may execute with `__file__` unavailable, so required DEX loading must not depend
only on `os.path.dirname(__file__)`.

Preferred order for structured EAF bootstrap:

1. use the public Elyx asset facade when it is available early enough;
2. if bootstrap requires a filesystem path, use a documented/imported runtime helper such as
   `file_utils.get_plugins_dir()` and keep the private-layout knowledge centralized in the
   bridge;
3. keep `__file__` only as an optional compatibility candidate, never the sole required path;
4. keep legacy embedded DEX only for the explicitly supported single-file compatibility path.

If a runtime helper is used, import/define it normally. A `globals().get("helper")` fallback for
a symbol that was never imported is not a valid fallback.

For ordinary non-bootstrap assets, prefer the public `elyx` asset facade rather than
constructing the private Elyx installation path.

Asset load diagnostics should preserve the first failure stage: resolution, read, empty file,
invalid DEX magic, class loader construction, or class linkage. A later `JVM plugin is not
loaded` message is not a substitute for the primary cause.

## Legacy compatibility path

The template can retain a legacy single-file build for transition/testing:

```text
just embed
  -> Python source containing embedded DEX payload
```

Rules:

- legacy embedding must not leak into the canonical EAF path;
- code needed only for legacy mode should be isolated and labelled;
- new features should not depend on the legacy artifact unless explicitly required;
- if legacy compatibility is removed, delete its tests/docs/tooling together rather than
  leaving a half-functional fallback.

## Ownership by layer

### Python should usually own

- plugin lifecycle and user-facing enable/disable behavior;
- settings and menu registration;
- Elyx assets/strings/settings;
- account-aware high-level SDK helpers;
- background orchestration and error reporting;
- deciding when to invoke JVM functionality.

### Kotlin/DEX should usually own

- performance-sensitive JVM hooks;
- logic that is substantially easier with native Java/Kotlin types;
- reusable JVM helper classes;
- complex reflection/Xposed code that benefits from compile-time structure;
- code whose Python↔Java interop overhead would be material in a hot path.

Do not duplicate the same state machine independently in Python and Kotlin. Choose one owner
and expose only the state/actions needed across the bridge.

## State and reload boundaries

Elyx reloads Python modules, but the Android process remains alive. A newly loaded DEX may
coexist in memory with older class-loader/static state if the previous generation did not
clean itself up.

Therefore:

- Python `on_plugin_unload`/eject must drop bridge references and stop Python-owned work;
- JVM `eject`/dispose should unregister hooks/listeners and clear long-lived static state;
- callbacks from an old generation must not continue calling a new Python plugin instance;
- background workers should carry a generation/cancellation check when races are possible.

## Template initialization/rename

When turning the template into a real plugin, update all identity surfaces together:

- Elyx `metainfo.yml` id/name/version compatibility fields;
- legacy top-level metadata while legacy mode remains supported;
- project/Gradle package and root name;
- Kotlin package declarations and JVM entry-class path;
- Python file name if the local workflow assumes it;
- JVM-side plugin id/static identity used by bridge/runtime state;
- CI/release artifact naming.

Structured Elyx ids currently allow only ASCII letters, digits and `_`, length 2–32. Do not
reuse a legacy hyphenated id in `metainfo.yml`.

Keep supported version surfaces synchronized (`metainfo.yml`, Python `__version__`, project
metadata/release input where used). Author is plugin-owned metadata and should remain freely
changeable; do not make a template-author value a CI invariant.

## Architecture review checklist

Before accepting a structural change, check:

- Is EAF still the canonical artifact?
- Does `refmap.yml` still resolve every declared path?
- Do declared directories exist as explicit archive directory entries where the installer
  requires them?
- Is `classes.dex` binary and singular in the archive?
- Is `main.py` still valid standalone Python source?
- Does required asset loading work when `__file__` is absent?
- Are local imports valid under Elyx module isolation?
- Is bridge ownership clear and does it preserve the first load failure?
- Can unload/reload cleanly retire the old generation?
- Does legacy compatibility still work if we claim it does?
- Does CI exercise the new contract rather than only syntax?
- For JVM/runtime changes, did a real installed EAF cross Python → JVM on device?
